# First login

The image never runs the Dux setup for root. On the first graphical session, `ultus-atomic-desktop.service` runs `dms setup headless --compositor hyprland --terminal ghostty --skip-existing` as that user. It writes only under the user's home: `~/.config/hypr/hyprland.lua` plus the `dms/*.lua` fragments, the Ghostty config, and the `hyprland-session.target` binding for `dms.service`. A user who already has a Hyprland config without the DMS includes, such as a dotfiles-managed account, skips the setup. DMS writes Hyprland config in Lua only and refuses a compositor older than 0.55, so the image pins a build that loads `hyprland.lua`.

The unit records success with `${XDG_STATE_HOME:-$HOME/.local/state}/ultus-atomic/desktop-setup.done`, matching the unit's `%S`. `ExecCondition` runs the setup for a fresh home or a dms-generated config without that marker, so a failed or timed-out run retries on the next login instead of leaving a half-written home skipped forever. The marker is written only after `dms setup` exits 0.

The desktop retry's failure contract is retry on the next login until it succeeds. Each attempt is capped at 120 seconds, and there is no attempt limit, so a permanently failing setup costs up to 120 seconds on every login. A cap is a pre-promotion follow-up. The greeter seed's contract is retry on the next boot, described below.

`ultus-atomic-dms-defaults.service` seeds `~/.local/state/dms/session.json` with a dark DMS background, so the first session is not a blank compositor surface. Replace it with a wallpaper from the Dux library when you want the full documented look.

Both units are enabled through `modules/desktop/usr/lib/systemd/user-preset/01-ultus-atomic.preset`, which the desktop module's build step applies with `systemctl --global preset` at build time. `dms.service` is not globally enabled: `modules/desktop/usr/lib/systemd/user/hyprland-session.target.wants/dms.service` binds it to the Hyprland session, so the shell starts for every Hyprland login, including an account that already owns a config and skips the setup. The binding relies on `hyprland-session.target`, which Hyprland 0.57 and newer ship. The COPR installs that unit under `/usr/lib64/systemd/user`, which `systemd-analyze --user unit-paths` does not list, so the build copies it to `/usr/lib/systemd/user` and fails if the installed package lacks it. The Xfce fallback never starts `hyprland-session.target`, so it never starts the Wayland shell. Both units skip root and the greeter account.

The greeter command comes from the module's `/etc/greetd/config.toml`, which names `dms-greeter --command hyprland` and overrides the package default that named niri. Do not copy Zirconium's `[general] service = "greetd-spawn"` stanza: Fedora's greetd 0.10.3 does not ship a `greetd-spawn` binary.

The greeter picks session index 0 when it has no memory, and the desktop files load in asynchronous order. `ultus-atomic-greeter-defaults.service` runs before `greetd.service` and seeds `/var/cache/dms-greeter/.local/state/memory.json` with `lastSessionDesktopId: "hyprland.desktop"`, so a fresh install always opens Hyprland. A session remembered from a previous login still wins, and any existing file, including an empty one, is left alone; delete it to re-seed.

The seed is a `Wants=` dependency, not `Requires=`, so a failed seed does not block the login. Its failure contract is retry on the next boot with the result visible in the unit journal; greetd then falls back to the first session it loads, which may be the Xfce fallback. Check `systemctl status ultus-atomic-greeter-defaults.service` after a first boot.

A real install creates the operator account itself, either in the installer or with `useradd -m`. The image never ships a login account or a password.
