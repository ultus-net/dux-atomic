# Known gaps before promotion

- The image has no application set or snapshot automation yet. The README marks these as planned.
- The NVIDIA variant is scaffolded in `Containerfile.nvidia` and `manifests/packages-nvidia.txt`, but it is not built in CI, locked, or published. The module path is decided: `akmod-nvidia` compiled during the image build, unsigned, as a documented exception, which means Secure Boot on NVIDIA hardware needs a per-machine MOK enrollment (#40). The compile runs in the build because `akmods.service` is skipped on an ostree-booted host and `/usr` is read-only at runtime. A local build of the variant succeeds, the kernel headers are checked against the installed kernel, and build 5 carries the five `nvidia*` modules with `version=620.70.06` and an empty signer; `docs/research/2026-11-14-nvidia-variant-build.md` records the build and the compile, and `docs/research/2026-11-14-nvidia-module-path-decision.md` the decision. Publish and a hardware boot remain (#72).
- Home snapshots are blocked on an install path that creates no home subvolume, and on four measurements a btrfs host must take. The layout is decided: a dedicated `home` subvolume, snapshotted alone (`docs/research/2026-11-14-btrfs-home-layout-decision.md`). The install command in `docs/install.md` passes only `--filesystem btrfs`, and `bootc install to-disk` documents a partition layout with no subvolume layout below it. Measured on the pinned base, `/home` is a relative symlink to `var/home` and the image creates no `/var/home`, so home lives in the root filesystem. btrbk processes btrfs subvolumes only, so a `subvolume home` line would snapshot nothing. `docs/research/2026-11-14-btrbk-home-layout.md` records the three ways forward and the four measurements. No btrbk package, timer, or configuration ships, and no restore drill has run (#68).
- The gaming layer ships Steam and its graphics stack, but no game has been launched from a built image. `ntsync-autoload` arrives as a weak dependency and its kernel module is unverified, and the layer lands on the Intel laptop as well as the gaming machine, because one image serves both.
- The developer and sysadmin layer ships a C toolchain, Node 22 with npm, btop, and a diagnostics set, but it is proven only by package presence and two runtime probes. `tests/verify-image.sh` runs `node --version` and `npm --version`, so the dotfiles npm globals can start, and the manifest-wide query proves every diagnostic binary's package is installed. No test runs a diagnostic, and nothing exercises the Homebrew bootstrap that the compiler exists for. `lazygit` and `yazi` stay outside the image because Fedora 45 carries neither, and `cmake` and `meson` stay outside because the split leaves native build systems to Homebrew or a Distrobox container. `docs/developer-tooling.md` records the split and these gaps (#67).
- The VM test covers the greeter and a serial login. It does not log in through the greeter, start a second session, or exercise the Xfce fallback.
- CI runs the boot test on TCG and does not render or inspect the desktop. The graphical dogfood stays a local pre-promotion step.
- The test disk raises `systemd.default_device_timeout_sec` to 180s so slow TCG boots reach `/boot`. CI therefore cannot catch a regression that only exceeds the shipped 45s.
- `bootc-image-builder` is pinned in `tests/vm/make-disk.sh`, and the base is pinned by digest, but `manifests/packages-common.lock` is a post-build drift gate rather than an install pin. `build/common.sh` installs by name from live repositories, so the gate rejects a third-party rebuild that already landed in the image. The lock now records NEVRA and the package `%{from_repo}` for every installed package whose origin repository is not a Fedora repository, which lets the gate catch third-party rebuilds even when they are pulled in transitively. The generator normalizes a COPR project's dependency repo id (`coprdep:`) to the project's main repo id (`copr:`) because which repository served a package can vary at build time; the NEVRA still pins what landed so this move is not treated as drift. The file still excludes Fedora-origin packages (so a Fedora updates bump does not red the gate) and excludes `+git` builds because they cannot be pinned; the VM boot test covers a broken `+git` build. A manifest name that resolves to a different Fedora package is not gated: the lock no longer records Fedora resolutions, because a versioned resolution was never compared, and the `rpm -q --whatprovides` assertion in `tests/verify-image.sh` is the only check that a name still resolves, which cannot tell a rename from another provider that satisfies it (#20). Two builds of the same commit can therefore differ (#2).
- The literal base `FROM` removes the `BASE_IMAGE` build argument the candidate-images plan used to build the NVIDIA variant from the same `Containerfile`. That variant needs its own pinned `FROM`, and `tests/test-static.sh` accepts any tag+digest pin, so the variant's base is covered once it names one.
- The base swap to `fedora-bootc` (#59) changes what the image inherits, so three things need a fresh check on the first booted build. `duxinstall` has not been run against it: the image claims to preinstall every dependency it probes, and a miss costs the user an `rpm-ostree install` and a reboot before the desktop. The duxlabs COPR packages now arrive on a Fedora-signed-kernel base rather than a Universal Blue one, so the first `image` run re-triages `.trivyignore` (the `base-main` entries belong to the old base). And no ublue package supplies the update, MOTD, or enrollment helpers any more: `bootc-fetch-apply-updates.timer` comes from the base preset, and the MOTD overlay is this repo's own.
- No NVIDIA path on this base, or on any base: an akmod compiled at boot carries no distribution signature, so Secure Boot refuses it until the module is signed locally. That is [#40](https://github.com/ultus-net/dux-atomic/issues/40), not a regression of #59.
- The first-login retry has unit fixtures and a VM marker assertion, but no partial-home VM coverage yet. Rebuild and re-run the graphical dogfood after the retry change.
- The attested SBOM lists packages only. `build/sbom-packages-only.jq` drops the 86111 file entries, the 85109 relationships that point at them, and the package verification codes that covered them, which takes the document from 64181348 to 6508304 bytes. Rekor's public instance answered 502 for the 86 MB DSSE body; a replay reached the service at 16 MB and was rejected at 32 MB. File-level hashes are therefore not attested, and a larger package set could approach the limit again. Every package now reports `filesAnalyzed: false`, because the codes covered a file inventory the document no longer carries.
- The trivy scan is blocking, but 37 CVEs and one GHSA from the duxlabs COPR Go binaries and the base image's Go binaries are ignored in `.trivyignore` until 2027-02-11. The fix belongs upstream: the `dms` and `dsearch` builds need the Go stdlib and module bumps their fixed versions name. The base swap did not stale them: every path an entry names still exists in the current image, checked on 2026-11-14 by listing `/usr/bin/dms`, `/usr/bin/dsearch`, `/usr/bin/cosign-linux-amd64` and `/sysroot/ostree/repo/objects` inside the local `ghcr.io/ultus-net/dux-atomic:latest`, so the entries still match and no re-triage is pending from #59. On the expiry date every entry is reported again and `image` reds, which forces a re-triage. No trivy run backed this check: `trivy` is not installed on the operator host, so the entries were matched by the paths they name rather than by a fresh advisory pass. An ignored finding is debt, not a clean scan (#3).
- The image ships no `/etc/containers/policy.json`, so a host does not verify the image it pulls or upgrades. `publish` signs the digest with keyless cosign OIDC, but a keyless policy cannot name this repository's workflow. `sigstoreSigned.fulcio` accepts only `caPath`/`caData`, `oidcIssuer` and `subjectEmail` (`image/signature/policy_types.go:162` through `:170`), and the verifier matches `untrustedCertificate.EmailAddresses` only (`image/signature/fulcio_cert.go:168`), while a GitHub Actions certificate carries the workflow as a URI SAN (`https://github.com/ultus-net/dux-atomic/.github/workflows/ci.yml@refs/heads/main`, the identity the `publish` job asserts). The limitation is recorded in `podman-container-tools/container-libs#388`: the issue is titled "Support Sigstore bundle format", and the URI-subject failure is its 2026-03-13 comment. The narrower `buildSignerURI` matcher is unmerged in `container-libs#625`, after `containers/image#2235` closed unmerged on 2025-08-26. A shipped policy therefore needs a release key referenced by `keyPath` plus a rotation plan, and that key does not exist yet. `tests/test-signing.sh` proves the accept and reject mechanism with a fixture key, and it cannot ship a trust root. The same library also cannot read cosign v3's default bundle format (#388), so the fixture stays on the v2.6.5 that `publish` pins.

- Signing trust root decided, release key named by `keyPath`, but no key and no policy exist yet, so a host still verifies nothing. `docs/research/2026-11-14-signing-trust-root-decision.md` records the decision and the custody answers, and the three remaining items are #4.

- No boot of this image with Secure Boot enabled has been recorded. Both policies are decided: no encrypted root on either target, and Secure Boot needs no per-machine enrollment because the base keeps Fedora's kernel. The unencrypted root means data at rest on both machines is unprotected, which is accepted rather than overlooked. The image's kernel is signed by `CN=kernel-signer` under `CN=fedoraca` and its in-tree modules by `Fedora kernel signing key`, which a Secure Boot machine trusts through Fedora's shim. `tests/verify-kernel-signature.sh` runs in the `image` job and fails unless the kernel's certificate table names `CN=fedoraca`, so a base bump cannot ship an unsigned kernel unnoticed. The VM test has neither Secure Boot nor a TPM, so CI still cannot reach firmware state. The desktop's out-of-tree NVIDIA module is unsigned and refused under Secure Boot, which is [#40](https://github.com/ultus-net/dux-atomic/issues/40). The decision, the measurement, and the remaining check worth adding are in `docs/research/2026-11-12-luks-secureboot-policy.md` (#54).
