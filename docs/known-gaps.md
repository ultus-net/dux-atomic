# Known gaps before promotion

- `console=ttyS0,115200` ships a serial getty to every install. It is a deliberate VM-test and recovery console for this branch; gate it behind a test build before publishing.
- The image has no NVIDIA variant, application set, agent sandbox, or snapshot automation yet. The README marks these as planned.
- The gaming layer ships Steam and its graphics stack, but no game has been launched from a built image. `ntsync-autoload` arrives as a weak dependency and its kernel module is unverified, and the layer lands on the Intel laptop as well as the gaming machine, because one image serves both.
- The VM test covers the greeter and a serial login. It does not log in through the greeter, start a second session, or exercise the Xfce fallback.
- CI runs the boot test on TCG and does not render or inspect the desktop. The graphical dogfood stays a local pre-promotion step.
- The test disk raises `systemd.default_device_timeout_sec` to 180s so slow TCG boots reach `/boot`. CI therefore cannot catch a regression that only exceeds the shipped 45s.
- `bootc-image-builder` is pinned in `tests/vm/make-disk.sh`, and the base is pinned by digest, but `manifests/packages-common.lock` is a post-build drift gate rather than an install pin. `build/common.sh` installs by name from live repositories, so a third-party rebuild is already in the image when `tests/verify-image.sh` rejects it. The lock covers only the packages the manifest names, so a rebuild of a package they pull in transitively, such as `quickshell` from `duxlabs/dux-repo`, changes the image without failing the gate (#20). The gate also keys on `%{VENDOR}`, a package-controlled string, so a third-party build that declares `Fedora Project` would be skipped. Fedora packages float with the updates repository on every build. A `+git` build is excluded from the lock and the gate, because it tracks an upstream branch and cannot be pinned; the VM boot test covers a broken one. Two builds of the same commit can therefore differ (#2).
- The literal base `FROM` removes the `BASE_IMAGE` build argument the candidate-images plan used to build the NVIDIA variant from the same `Containerfile`. That variant needs its own pinned `FROM`, and `tests/test-static.sh` matches `base-main` only, so the NVIDIA image needs a matching assertion before it lands.
- The first-login retry has unit fixtures and a VM marker assertion, but no partial-home VM coverage yet. Rebuild and re-run the graphical dogfood after the retry change.
- The attested SBOM lists packages only. `build/sbom-packages-only.jq` drops the 86111 file entries, the 85109 relationships that point at them, and the package verification codes that covered them, which takes the document from 64181348 to 6508304 bytes. Rekor's public instance answered 502 for the 86 MB DSSE body; a replay reached the service at 16 MB and was rejected at 32 MB. File-level hashes are therefore not attested, and a larger package set could approach the limit again. Every package now reports `filesAnalyzed: false`, because the codes covered a file inventory the document no longer carries.
- `publish` caps each signing and attestation attempt at five minutes, each command's retries at ten minutes over at most five attempts, and each verification call at three, so a permanent error costs up to about half an hour before the run goes red. The step is bounded; the job is not, because `podman push` before it has no cap. Run 42827200322 stalled in that step for 51 minutes and the job timeout destroyed the log, which is why the caps exist. Nothing has yet published a signature and an attestation in one green run. The digest check-run annotation has not yet been seen on a timed-out job, so its survival is unproven. A sign that succeeds server-side but times out client-side is retried, and no run has exercised that duplicate signature.
- The image ships no `/etc/containers/policy.json`, so a host does not verify the image it pulls or upgrades. `publish` signs the digest with keyless cosign OIDC, but a keyless policy cannot name this repository's workflow. `sigstoreSigned.fulcio` accepts only `caPath`/`caData`, `oidcIssuer` and `subjectEmail` (`image/signature/policy_types.go:162` through `:170`), and the verifier matches `untrustedCertificate.EmailAddresses` only (`image/signature/fulcio_cert.go:168`), while a GitHub Actions certificate carries the workflow as a URI SAN (`https://github.com/ultus-net/dux-atomic/.github/workflows/ci.yml@refs/heads/main`, the identity the `publish` job asserts). The limitation is recorded in `podman-container-tools/container-libs#388`: the issue is titled "Support Sigstore bundle format", and the URI-subject failure is its 2026-03-13 comment. The narrower `buildSignerURI` matcher is unmerged in `container-libs#625`, after `containers/image#2235` closed unmerged on 2025-08-26. A shipped policy therefore needs a release key referenced by `keyPath` plus a rotation plan, and that key does not exist yet. `tests/test-signing.sh` proves the accept and reject mechanism with a fixture key, and it cannot ship a trust root. The same library also cannot read cosign v3's default bundle format (#388), so the fixture stays on the v2.6.5 that `publish` pins.
