# CI and publishing

`.github/workflows/ci.yml` runs on every pull request, every push to `main`, and manual dispatch. Every action is pinned to a commit SHA, and the job that runs PR code holds only `contents: read`.

- `static` runs `tests/lint.sh`: shell syntax, shellcheck, hadolint, actionlint, and `tests/test-static.sh`. The script pins the linter images by digest. `tests/test-static.sh` also asserts the base pin's tag+digest form, rejects a returning `ARG BASE_IMAGE`, and checks the package lock's header, `<nevra> TAB <vendor>` format, and ordering. `just check` runs the same script.
- `image` builds the image, runs `tests/verify-image.sh` (`bootc container lint`, `systemd-analyze verify`, the package assertions, and the third-party lock comparison), generates an SPDX SBOM with syft, trims it with `build/sbom-packages-only.jq` so the attestation fits Rekor's request limit, builds the qcow2 with bootc-image-builder, and runs `boot-smoke.sh` on QEMU TCG with an 1800s boot timeout and a 300s `greetd` grace. The boot test asserts the greeter session through `loginctl` after a serial login, not rendered pixels. A hosted runner has no `/dev/kvm`, and run 43068532421 measured a 275s guest boot at roughly 4.6x wall-clock slowdown, so the login wait needs the better part of half an hour and the job's `timeout-minutes: 180` still bounds it (#50). The getty prompt is matched by hostname, not by an end-of-line anchor, because a kernel message can land on the prompt's line: that run printed `fedora login: [ 275.126011] clocksource: Watchdog ...` and the anchored pattern missed it. It then scans with a digest-pinned trivy container, and the scan is blocking: `.trivyignore` holds the triaged findings in the duxlabs Go binaries and the base image's `sysroot/ostree/repo/objects` copies, each with an expiry date and the fixed upstream version beside its group, so a new finding or an expired entry reds `image`. The report uploads even when the scan fails, so the evidence survives (#3). Every job installs its runner packages through `build/install-packages.sh`, which retries the install up to three times inside a 300s budget and caps each attempt at 180s, so the worst case still fits `promote`'s ten-minute job bound (#46). Run 43033654470 lost a promotion to `Temporary failure resolving` in this step, and run 43052107613 spent the whole budget on `Ign:` lines for `azure.archive.ubuntu.com` without reaching the next mirror. The script therefore keeps apt at one fetch attempt per URI and comments the Azure entry out of the runner's mirror list after a failed attempt, because apt spends every retry on the same URI before it re-ranks the list. A mirror that stays slow through all three attempts still fails the job.
- `signing` runs `tests/test-signing.sh` on every CI trigger, after `static` and with no write token. It starts a digest-pinned `registry:2` on localhost, pushes two payload tags with different digests, signs the trusted tag with a fixture keypair and the untrusted tag with a second key outside the policy, and asserts four outcomes: a signed tag and a signed digest both verify, an unsigned tag is rejected because no signature exists, and the untrusted key's signature is rejected because verification failed. It runs the cosign version `publish` pins, because key-based signing needs the legacy `.sig` attachment format that containers/image can read (container-libs#388).
- `publish` runs only on `main`, holds the write token, OIDC identity, and `attestations: write`, and checks out the repository only to run the shared package installer: it never builds image content. It loads the built artifact, pushes `:sha-<commit>`, signs the digest with cosign keyless OIDC, attests the SBOM with `--new-bundle-format`, and attests build provenance for that same digest with `actions/attest`, which binds the digest to this workflow run (#5). The bundle format is not cosmetic: `cosign verify-attestation` switches to bundle-only discovery once any Sigstore bundle references the digest (`cosign.GetBundles` in `cmd/cosign/cli/verify/verify_attestation.go`), so the legacy tag attachment becomes invisible. Run 43106659542 failed `verify` in 12s that way, reporting `none of the attestations matched the predicate type: spdxjson, found: https://slsa.dev/provenance/v1`. `create-storage-record: false` keeps `artifact-metadata: write` out of the job, because nothing here reads a linked-artifact record. A first step writes the `with_log` and `retry` helpers to `$RUNNER_TEMP/helpers.sh`, and each signing step sources that file and runs its own bounded commands, so a hang names the step it came from. Signing and attesting each retry up to five times with a 30s pause that doubles to 240s, each attempt is capped at five minutes, and each command gets a ten-minute budget, so a genuine 5xx or network failure rarely fails the only publish path while a stalled connection still ends with a message inside the job's 60 minutes. Sign and attest carry their own `timeout-minutes: 15`: run 42933898962 was cancelled by the job's 60-minute cap without firing the single step's 40-minute bound, and run 42943634705 ran 51 minutes past it, so the work is split instead of trusted to one step bound. The pushed digest is emitted as a check-run annotation by its own step immediately after the tag push, before any signing, but the annotation did not survive the job cap on check-run 130340952461, so the publish log is the durable record. Each signing command writes its output to a file under `$RUNNER_TEMP`, and the file is printed after the command returns through `head -c 20000`; when the file is larger than 20000 bytes, a line reports its total size so the cut is visible. The bound is there because `cosign verify-attestation` prints its payload with `fmt.Println` and the attested SBOM is about 8.7 MB on one line, which stalled the runner's log pipeline in run 42981185735 (`actions/runner#1031`). A final `if: always()` step uploads `$RUNNER_TEMP/*.log` as the `publish-logs` artifact, so the steps that ran keep their logs when a later one dies. A job that reaches its own 60-minute cap still drops the pending upload, which is the path every hung run has taken so far (#26).
- `verify` runs after `publish` with only `contents: read` and `packages: read`, and holds no OIDC identity. It logs in to GHCR, installs the same cosign version `publish` pins, and runs `cosign verify` and `cosign verify-attestation` against the digest `publish` exports, each under a three-minute `timeout --kill-after` and an eight-minute step bound, then runs `gh attestation verify` against the same digest with `--bundle-from-oci`, which reads the bundle from the registry instead of the attestations API, and `--cert-identity` pinned to `ci.yml` on `refs/heads/main`, the same identity the cosign checks use, so an attestation from another workflow, repository, or branch fails (#5). The job carries `timeout-minutes: 20`, because a stall here survived both a command timeout and a step timeout: run 42961488922 signed in 4s and attested in 5s, then held the combined verification step from 05:32:56 to the job's 60-minute cap without a log or an annotation. Only a job boundary did end it, and moving it out keeps `publish` green so the main queue drains. Each cosign call sends stdout to `$RUNNER_TEMP/verify.log` or `verify-attestation.log`, prints only a 20000-byte prefix, and leaves stderr on the step log so a failed check stays visible, while `gh attestation verify` sends both streams to `verify-provenance.log` and reads the workflow token from `GH_TOKEN`, and the step names a missing CLI or token instead of failing inside the verification command; an `if: always()` step uploads those logs as the `verify-logs` artifact on every outcome. A red `verify` still blocks `:latest`.
- `promote` runs only on a `workflow_dispatch` on `main` with `promote` set, and needs both `publish` and `verify`. It copies the signed manifest to `:latest` and asserts the registry digest. A failed copy leaves the previous tag and fails the run, so a human retries. A push never moves `:latest`.
- A `workflow_dispatch` on `main` with `publish` set and `promote` unset publishes the commit it runs on without moving `:latest`. A dispatch with neither input runs `static`, `signing`, and `image`, so a green run does not always publish.
- `static` and `image` are required checks on `main`; a red hosted `image` run blocks merge. `signing` runs on every trigger but is not a required check, so a red signing run shows on the PR without blocking it.
- The `ghcr` environment is the approval hook. Add required reviewers in the repository settings to gate publication.
- The first push creates a private GHCR package. Set the package visibility to public in the package settings if anonymous pulls are wanted.

The SBOM step scans a flattened rootfs with a digest-pinned syft container. syft needed more than 8 GB to scan the docker archive, so the step exports the image first, and it writes the report to a file rather than buffering it in memory.

`just check` mirrors the static gate. `just build`, `just lint-image`, `just disk`, and `just boot` cover the rest.
